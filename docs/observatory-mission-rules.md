# 관측소 작업 규칙

> 부실 조기경보 관측소(`/observatory`) 관련 작업은 모두 이 규칙을 따릅니다.
> 출처: 사용자 지시(2026-10-18, 미션 2). 원문을 그대로 옮겼습니다.

1. 운영: 사용자에게 질문하지 않는다. 설계·기준·범위·문구는 스스로 결정하고 이유를 결정 로그에 남긴다. 사람이 결정할 것은 되돌릴 수 없는 일뿐이다: 사이트 공개, 비용이 생기는 연결, 새 계정·API 키 발급, 데이터·코드의 되돌릴 수 없는 삭제, 비밀키 노출, 법·규제 관련 주장. 이런 일은 하지 말고 로그의 "사람이 결정할 항목"에 적는다. 막히면 우회한다(정직하게 표시한 대리 지표, 또는 미구현+이유). 멈추지 않는다.
2. 사이트 문구: 모두 존댓말. 사이트 어디에도 사이트의 제작·구성·작성 주체가 AI이거나 AI의 도움을 받았다고 읽히는 표현을 넣지 않는다(예: "AI가 분석", "AI 생성", "AI 어시스턴트", "AI가 작성", 생성형 모델·챗봇·자동 생성 글을 제작 도구로 언급하는 표현, 도구·제작사 이름). "AI"라는 단어 자체는 금지가 아니며, 투자·산업 주제로서의 AI(예: AI 설비투자, AI 데이터센터, AI 기업)는 써도 된다. 사실/해석/확인 못함을 분리한다. 직접 측정이 아닌 지표는 "대리 지표"임을 한계 문구에 정직하게 쓴다. 각 상세 페이지에 한계 문구, 시차 문구(실제 발표 일정과 이 사이트 반영 시점), "위기를 미리 알려 주는 용도로 검증된 것이 아니다" 취지의 문구를 넣는다. 숫자 표기는 기존 카드 규칙(십억 달러 등)을 따른다.
3. 기술: cron은 GET 전용(POST는 405로 조용히 실패). Upstash Redis는 JSON.stringify/parse 없이 객체를 그대로 저장. 시장·계정 코드는 이름이 아니라 코드/ID로 조회. 수집기는 독립 try/catch, 실패하면 기존 저장분 유지하고 에러를 던져 cron errors에 남긴다. 결측은 지표 성격에 따라(잔액·금리·예금은 건너뜀, 흐름성은 0). 서버 컴포넌트에서 "use client" 파일의 함수를 호출하지 않는다(공통 함수는 format.ts). 빌드 통과 ≠ 실행 정상이므로 npm run build && npm start로 실제 요청을 확인. Recharts: 색은 hex 하드코딩, 막대 색은 Cell, ReferenceLine 라벨은 플롯 안쪽 위치, 모바일 x축 간격 자동. 모바일 390px에서 페이지 가로 스크롤이 없어야 하고 표는 감싸개 안에서만 스크롤. 목록·섹션·navbar는 lib/observatory-catalog.ts에서 자동 생성되므로 손으로 추가하지 않는다(snapshots.ts LOADERS, summaries.ts SECTION_SUMMARIZERS 등록은 필요). cron 실행 시간(60초 한도)을 재서 안전하지 않으면 병렬화하거나 분리.
4. 판정: 추세적으로 커지는 시계열은 수준이 아니라 변화(증가율·금액 변화)로 본다. 분모가 0에 가까워질 수 있는 비율은 쓰지 않는다. 데이터 단절·재분류·계정 재편을 먼저 확인하고 공개된 것은 보정하거나 표시한다. 분포 기준은 각 시점까지의 데이터만으로 계산하고 최소 표본(157주 등) 전에는 판정 보류. 규칙은 사전에 선언해 근거를 코드 주석에 남기고 한 번만 적용한다. 결과가 나빠도(상시 경보, 사건 미포착) 기준을 반복 조정하지 않고 그대로 보고·공개한다. 주의+경보가 판정 가능 기간의 15%를 넘으면 "상시 경보 위험"으로 명시. 명백한 데이터 오류만 고친다. 외부 사건 날짜는 외부 출처로 확인되는 것만 회귀 검증에 쓴다.
5. 검증(두 겹): A) 만드는 쪽: tsc, lint, build, 프로덕션 모드 요청 확인, 원본 출처를 새로 받아 별도 스크립트로 독립 계산해 저장값과 전 기간 불일치 0건, 회귀 검증 표, 전 기간·연도별 발동 횟수(연도별 합계가 전체 주·일 수와 정확히 맞는지), 신규 페이지·API 200, cron 401/200과 errors 비어 있음, cron 실행 시간, 제작 주체 암시 표현 검사(사용자 노출 문구에서 "AI"가 나오는 모든 위치를 목록으로 뽑아 각각이 주제로서의 언급인지 확인하고, 규칙 2의 예시 표현과 Claude, Anthropic, 챗봇, LLM, 생성형, 어시스턴트, 자동 생성이 0건인지 확인), 평서체 grep, 데스크톱·모바일 브라우저 확인. B) 독립 검증: 별도 서브에이전트에게 만든 쪽 컨텍스트와 결론을 주지 않고 코드·배포된 페이지·원본 출처만 주고 "틀린 것을 찾아라"라고 시킨다(원본 재계산, 문구의 사실 오류·과장·존댓말·제작 주체 암시 표현, 한계 문구의 정직성, 판정 경계 조건, 로그와 코드 불일치). 지적마다 고치거나 재현 가능한 증거로 반박하고 둘 다 로그에 기록. 증거 없이 반영하지 않음으로 넘기지 않는다. 수정하면 A를 다시 돌린다.
6. 문서화: docs/observatory-decision-log.md(관측소·지표별 출처/주기, 규칙과 근거, 사실·해석·확인 못함, 회귀 결과, 발동 비율, 한계, 단절 처리, 사이트가 독자에게 하는 주장 원문 모음, 독립 검증 지적과 처리, 사용자 정정, 사람이 결정할 항목, 공개 전 체크리스트, 남은 위험)를 쉬운 한국어로 갱신. docs/observatory-progress.md에 단계별 진행 상태(어디까지 push됐고 다음 할 일)를 계속 갱신해 새 세션이 이어받을 수 있게 한다.
7. 불변 기준값은 미션 내내 유지(아래 기준 상태).
8. 커밋·푸시: 검증을 모두 통과한 뒤에만, 이번 작업 파일만 git add(루트의 CURRENT_TASK.md는 건드리지 않음), 기존 커밋 메시지 스타일, 현재 브랜치(master)에 push. push 후 배포가 끝나면 배포 사이트에서 같은 URL들을 다시 확인하고 cron을 수동 호출해 errors가 비어 있는지 확인.
